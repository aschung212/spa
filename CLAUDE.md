## Design Principles

Follow these in every UI decision:

1. **iOS HIG is the north star.** Every component should feel like it belongs in a native iOS app. Use Apple's Human Interface Guidelines as a checklist: 44pt touch targets, SF-style typography scale, progressive disclosure, grouped settings.

2. **No feature bloat.** Before adding a feature, ask: does this duplicate something that already exists? If tags already solve the problem, don't add templates. Every feature must earn its place. When in doubt, don't add it.

3. **Progressive disclosure.** Show the minimum needed at each level. Details expand on tap. Settings are grouped. Modals drill down, not sideways. The user should never see 10 options when 3 will do.

4. **Visual over verbal.** Surface information at the right moment through visual cues — tappable banners, color changes, badges, toasts — not through text-heavy explanations or separate screens.

5. **One interaction path, not three.** Enhance existing patterns rather than adding parallel ones. If there's already a way to do something, make that way better instead of creating an alternative.

6. **Consistent modal patterns.** Use bottom sheets for settings, centered modals for detail views, inline expansion only when the content is small. Don't mix paradigms within the same feature area.

## UI Change Checklist

Before committing any UI change, verify all of the following:

- [ ] Touch targets are 44pt minimum (buttons, toggles, tappable rows, icons)
- [ ] Uses theme CSS custom properties (`var(--color-*)`) — never hardcoded colors
- [ ] Text uses the app's type scale — no arbitrary font sizes
- [ ] Spacing uses the 4/8/12/16/24/32 scale — no arbitrary pixel values
- [ ] Modals use existing bottom-sheet or centered-modal pattern — no new modal paradigms
- [ ] No new navigation patterns introduced — stay consistent with existing tab/modal structure
- [ ] Component renders correctly in all 10 themes, both light and dark mode
- [ ] New interactive elements have appropriate aria attributes
- [ ] Animations use CSS transitions/animations, not JavaScript timers
- [ ] No layout shift when showing/hiding conditional elements — reserve space or position at end of row
- [ ] Scrollable content has `-webkit-overflow-scrolling: touch` where needed
- [ ] Icons are consistent with existing icon style (SVG stroke icons, 24x24 viewBox)

## Capacitor / Native iOS Readiness

This app will be wrapped with Capacitor for the App Store. Keep all code compatible:

- No Web APIs unavailable in WKWebView (no Web Bluetooth, WebUSB, Web Serial, etc.)
- No browser-specific behavior (no `window.confirm()`, `window.prompt()`, `alert()` — use custom modals)
- Touch interactions only — no hover states as primary affordances (hover can enhance, never gate)
- Use `env(safe-area-inset-*)` for notch and home indicator spacing on all fixed/sticky elements
- No hard dependencies on browser URL bar, back button, or browser navigation
- localStorage and IndexedDB are available in Capacitor — these are safe to use
- The service worker is **disabled entirely on the native Capacitor build** (#532). WKWebView serves the web assets bundled in the `.ipa` and refreshes them via `cap sync`, so a Workbox SW is redundant and risks reload loops / stale caches. This is enforced in two layers: `useServiceWorker` skips `registerSW` at runtime when `isNative`, and `vite.config.js` sets `VitePWA({ disable: true })` when `CAPACITOR_BUILD=true`. **Always build the native bundle with `npm run cap:build`** (it sets that env var) — a plain `npm run build` would bundle a SW into the native app.
- Avoid `position: fixed` layouts that break when the iOS keyboard opens — use `visualViewport` API or bottom-sheet patterns that account for keyboard

## iOS Compliance

This app targets iOS App Store via Capacitor. Every UI element must meet Apple's Human Interface Guidelines:

- **44pt minimum touch targets.** Buttons, toggles, tappable rows, icon buttons — all must be at least 44x44pt. Existing regression tests enforce this for known violations. When adding new interactive elements, verify and add a test. Two ways to reach 44pt, and the choice is not free: size the element (`min-height: 44px`) by default, or keep a compact visual and extend the hit area with an absolutely-positioned transparent `::before` (`.logSetFieldClear`). The overlay is only safe for a control ringed by inert whitespace — for controls that **tile**, like the `.wtTagPickerChip` rows (#990), overlays butt against each other and a near-miss activates the neighbour instead of doing nothing, so size those instead.
- **Safe area insets.** All fixed/sticky elements must use `env(safe-area-inset-*)`. The Dynamic Island on newer iPhones hides content at the top. Test in PWA standalone mode — browser mode hides this issue.
- **WCAG 2.1 AA contrast.** All 10 themes (20 variants) are tested via `themeContrast.test.ts`. When adding or modifying theme colors, run the contrast audit. Normal text needs 4.5:1, large text needs 3:1.
- **Pinch-zoom stays enabled, so every text control is ≥ 16px (LIFT-1376).** `index.html` shipped `maximum-scale=1.0, user-scalable=no` — pinch-zoom disabled outright, failing WCAG 2.1 AA 1.4.4 (Resize Text) and 1.4.10 (Reflow) and a scored Lighthouse a11y audit, while `index.css` commented that the `--font-*` scale is rem-anchored *specifically* so text honors Dynamic Type. The CSS claimed a compliance the meta tag revoked one file away, and nothing caught it because `metaRegression.test.ts` only ever pinned URLs. **The two halves are one change.** That lock was also suppressing iOS Safari's zoom-on-focus, and seven controls computed under 16px behind it (`.wtSearchInput` 14, `.settingsInput`/`.deleteConfirmInput`/`.wtTagManagerInput` 15, `.wtTagInlineInput` 13, `.recDaysInput` a hardcoded 14, `.wtDateOverlayInput` no declaration at all) — so dropping the lock alone would have traded a WCAG failure for a layout that yanks and never zooms back on every tap. All seven are now `var(--font-callout)`; two needed a width bump to match (`.wtTagInlineInput` 96→128, `.settingsInput` 96→112, the latter because its widest value is a `type="date"` rendering "12/28/2026"). Three things to know before touching this. (1) **A control with NO font-size rule fails too** — form controls do not inherit `body`'s font-size, they fall back to the UA default (~13px), which is how an invisible `opacity: 0` date overlay became a zoom trigger. (2) The floor covers **`type="date"` and `<select>`**, not just text fields; only types that never open a keyboard (`range`, `checkbox`, `radio`, `file`, `hidden`, submit/reset/button/image) are exempt. (3) The guard is **derived, not enumerated** — `cssRegression.test.ts` reads every `<input>`/`<textarea>`/`<select>` out of the `.vue` templates and resolves its `font-size` against `index.css` plus that component's scoped block, because a hardcoded class list would only pin the controls that existed when it was written and the two halves of the rule live in different files. It is deliberately **stricter than the cascade**: every rule that can style a control must clear 16px, not just the winner — resting a WCAG floor on source order is exactly how `.wtTagManagerInput` came to carry a dead 15px declaration that only looked harmless because `.repMaxInput` sits further down the file. If an input starts zooming on focus, raise its font-size; never re-add the viewport lock.
- **No hover-gated interactions.** Touch-only. Hover can enhance but must never be the only way to access functionality.
- **Every `role="switch"` needs an accessible name (LIFT-1308).** A toggle built as a `<button role="switch">` around a decorative knob `<span>` has none — `aria-checked` gives the state and the role gives the role, so AT announces "switch, off" and nothing about what it toggles (WCAG 4.1.2, Level A). All three `.iosToggle` switches shipped that way, two of them in the same sheet, announced identically. Prefer **`aria-labelledby` pointing at the visible row label** over a duplicated `aria-label` string: the accessible name is then the visible text by construction (WCAG 2.5.3) and a copy change can't leave the two out of sync. The name must also be **static** — state belongs in `aria-checked`, so the `:aria-label="on ? 'Disable x' : 'Enable x'"` shape the older `.glassToggle` rows use re-announces the control on every tap and is not the pattern to copy. Enforced structurally by `architecturalInvariants.test.ts`, which **derives** every `role="switch"` from the `.vue` sources and fails any with no `aria-label`/`aria-labelledby` and no text content. That derivation is the point: `accessibility.axe.test.ts` scans a hardcoded list of three components, so a switch anywhere else is invisible to it — LIFT-1304 hit exactly this and scoped its own axe scan *around* the violation rather than failing on it. With the switches named, that scan now covers the whole `WorkoutTracker`.
- **A custom `role="button"` must re-supply the whole button (LIFT-1305).** A native `<button>` takes focus and is activated by BOTH Enter and Space for free; an element that only borrows the role keeps none of that, so `role="button"` + `tabindex="0"` + `@keydown.enter` + `@keydown.space.prevent` travel together — the shape `TagManagerModal`, `GymManagerModal`, `ExerciseManagerModal` and `CalendarView` already use. It is the right shape only when the control wraps NO other interactive element — when it does, the answer is the row disclosure below (LIFT-1349), not this, which is why `BodyweightTracker`’s entry row no longer appears in that list. A partial job is worse than none: the control announces as a button, takes a tab stop, and then swallows the key the user was told to press (Space just scrolls the sheet behind it). Three of the four to-beat cards in the log sheet shipped as bare `@click` divs — unreachable by keyboard or switch control, WCAG 2.1.1 Level A — while the fourth sibling in the same `v-else-if` chain carried role/tabindex/Enter, which is what made it an omission rather than a convention. Two consequences beyond the keys. (1) **Conditionally-interactive cards bind role and tabindex to the same flag that makes them look tappable** (`:role="plateMode ? 'button' : undefined"`) — an informational card that takes a tab stop and does nothing is its own 2.4.3 problem. (2) **`tabindex` implies a `:focus-visible` ring**: the app resets no outlines, but `--accent-subtle` (8–12% alpha) is the *input* ring, paired there with a border-colour change, and would not clear the 3:1 non-text floor alone — use `outline: 2px solid var(--accent)`. Enforced structurally by `architecturalInvariants.test.ts`, which **derives** every literal and bound `role="button"` from the `.vue` sources: a hardcoded list would only pin the call sites that existed when it was written, and axe cannot see a missing key handler at all — that is a behaviour, not an attribute.
- **A tap-to-reveal row is a disclosure: a real `<button>` trigger with the actions as SIBLINGS (LIFT-1349).** Three lists render the same row — tap it, an inline `.wtSetActions` bar with **Edit** and **Delete** expands: `WorkoutTimeline`, `ExerciseDetailModal`, and `BodyweightTracker`. Two of them were bare `<div @click>`s with no role, no tabindex and no key handler, and that row is the **only** path to editing or deleting a logged set — so a keyboard or switch-control user could log all day (every control in the log sheet is a real `<button>` or an input) and never correct or remove one. WCAG 2.1.1, Level A, on a corrective-and-destructive path with no alternative. The third had `role="button" tabindex="0"` plus hand-rolled `@keydown.enter`/`@keydown.space.prevent`, and copying *that* would have been the wrong fix twice over: the `button` role is **children-presentational**, so the Edit/Delete buttons it wrapped are dropped from the accessibility tree (axe `nested-interactive`), and a `role="button"` `<li>` inside a `<ul>` additionally fails `aria-allowed-role`. All three are now `<container class="wtSetRow|wtTimelineRow"><button class="wtSetRowMain|wtTimelineRowMain" aria-expanded aria-label>…</button><div class="wtSetActions">…</div></container>` — Enter and Space come from the platform, so there is no key handler to forget. Two consequences that are easy to get wrong: (1) **the row's padding must move onto the trigger** (`.wtSetRow`/`.wtTimelineRow` are `padding: 0`, the trigger is `padding: 12px 16px; min-height: 44px; width: 100%`, and `.wtSetActions` carries its own inset) — a button sized to its text inside a padded row is a ~20px tap target where the row was 44px, i.e. fixing the keyboard path by breaking the touch one; (2) **the `aria-label` is required, not decorative** — the day a row belongs to lives in an unassociated `.wtSetDateHeader`/`.wtTimelineDateHeader` above the card, so without it AT cannot tell one day's sets from another's, and the timeline row's text otherwise ends on a bare `~228`. Keep the label **static** per row (state is on `aria-expanded`), per the switch rule above. **axe cannot catch the original defect** — a missing key handler is a behaviour, not an attribute — so the guards are structural (trigger is a `BUTTON`, row has no `role`, `.wtSetBtn` is not a descendant of the trigger) with an axe scan of the **expanded** row alongside to pin the nesting. `accessibility.axe.test.ts` had only ever scanned `BodyweightTracker` in its EMPTY state, which is why the one list with a keyboard path still shipped two axe violations nothing had ever looked at.

## Code Standards

- **TypeScript strict mode.** All new files must be `.ts` or `.vue` with `lang="ts"`. No `any` types unless absolutely necessary.
- **Conventional commits.** Format: `type: description (closes #NNN)` or `type(scope): description (#PR)`. Types: feat, fix, test, chore, docs, perf, refactor. (Project migrated from Linear to GitHub Issues on 2026-04-03; the old `LIFT-XXX` prefix is no longer used.)
- **ESLint clean.** Run `npm run lint` before committing. Zero errors allowed, warnings should be addressed.
- **No app-breaking changes.** Always run `npm test` and `npm run build` after changes. If tests fail, fix them before moving on.

## Testing Philosophy

Tests are not just for coverage — they prevent specific classes of regression:

- **CSS structural tests** (`cssRegression.test.ts`) — verify properties are in the correct CSS rule (not accidentally moved between base/override rules)
- **Meta tag tests** (`metaRegression.test.ts`) — pin all URLs to the real deployment domain, block hallucinated domains
- **WCAG contrast audit** (`themeContrast.test.ts`) — every theme variant checked against AA minimums
- **Manifest tests** (`manifestRegression.test.ts`) — verify PWA manifest fields and screenshot assets exist
- **Spacing scale tests** — enforce the 4/8/12/16/24/32 scale, flag off-scale values
- **RLS invariant** (`architecturalInvariants.test.ts`, LIFT-1130) — scans `supabase/migrations` and fails the build if any `create table` lacks a matching `enable row level security`, or if a `user_id`-scoped table has no `auth.uid()` policy. RLS is the *only* real tenant boundary (the anon key ships in the client bundle), so **every new table MUST enable RLS and add its policies in the same migration** — a table without RLS silently exposes every user's rows.
- **Frozen-clock invariant** (`architecturalInvariants.test.ts`, #1254) — any test file calling `calculateBest1RM` or `scoreSet` must also call `vi.setSystemTime`. Those two measure their 6-month window from `Date.now()` (every other now-relative helper — `promptArbiter`, `coachHistory`, `useAppReview` — takes `now` as a parameter instead), so a fixture written with an absolute date is asserting against the calendar and expires on its own: `progressionIntegration.test.ts` chose a date five months of wall-clock ahead of its own expiry and took `master` red, blocking every open PR. **A test that reads the clock must pin it** — freeze with `vi.setSystemTime`, then derive fixture dates from that frozen now (offsets, not literals) so the test measures the window rather than the day it was written.
- **Real-DB schema-drift suite** (`supabaseIntegration.test.ts`, #1283) — the only test that hits a real Postgres/PostgREST, run by the scheduled `Integration Tests` workflow (never on PRs; that gap is #1011). It holds the **service_role** key, which bypasses RLS but **not foreign keys** — Postgres enforces those from the table definition regardless of role. Every synced table declares `user_id uuid not null references auth.users(id) on delete cascade`, so a test must mint a REAL auth user (`createTestUser` → `supabase.auth.admin.createUser`) rather than invent a UUID; inventing one fails every insert with SQLSTATE 23503, which is why the suite failed all 95 of its scheduled runs — never once green — from May to August 2026. Cleanup hard-deletes the auth user and lets the FK cascade take the domain rows, so **a new synced table needs no change to `afterEach`**. The suite `describe.skip`s itself when `SUPABASE_INT_URL`/`SUPABASE_INT_SERVICE_ROLE_KEY` are unset (a local no-op), which is why the workflow's credential step now hard-fails on an empty key — otherwise the job reports green having run zero tests.


Most tests run under **happy-dom** (`vitest.config.js`), which has no layout engine — `offsetHeight`/`scrollTop`/`getBoundingClientRect` report 0. Layout- and gesture-sensitive composables (`useSwipeToDismiss`, `useFocusTrap`, viewport logic) additionally get a real-Chromium **Browser Mode** suite: `*.browser.test.ts` files run under `vitest.browser.config.js` via `npm run test:browser` (opt-in; `@vitest/browser`/`playwright` kept out of the lockfile like lhci). The default suite excludes the `*.browser.test.ts` glob. See `docs/browser-mode-testing.md`.

Every bug fix must include a regression test in the SAME commit. Before writing the test, ask: why didn't existing tests catch this? If it's a new class of failure, add a new test category.

## Settled Patterns (do not redesign)

These patterns were reached through multiple iterations of user testing. Do not refactor or "improve" them without explicit user request.

- **Set logging modal layout:** Title (exercise name) → date subtitle (tappable) → Suggestions drawer (consolidated ladder / intensity lenses, see Architecture Notes) → contextual e1RM/PR-target card → weight/reps side-by-side → plate calculator → Save/Done buttons. Buttons must always be last. The modal stays open after saving with fields cleared for the next set. Weight input auto-focuses after save. Modal is anchored to top of screen (`align-items: flex-start`) so inputs stay above the keyboard. Save/Done live in a sticky action bar pinned to the bottom of the log sheet (`.logSetSheetForm .repMaxActions` — flex-column sheet, `margin-top: auto`, `position: sticky`) so they are always visible without scrolling; form content scrolls behind the frosted bar. Do not move the buttons back into the scroll flow. The header row flanks the centered title with two 44pt icon buttons, shown only when logging for a real exercise (`isLogForExercise`): a leading **history** button (`.wtLogHistoryBtn`) and the trailing settings gear (`.wtPlateSettingsBtn`, opens EditExerciseModal). The history button (`openHistoryFromLog`, #971) jumps to the exercise's detail/sets view — because the log sheet and `ExerciseDetailModal` share a z-index (both `.repMaxOverlay`, `z-index: 100`), it is a **swap** (`closeModal()` → `openDetailModal(id)`), not a stack; the detail view's `+ Log Set` footer is the labelled path back to logging.
- **Date in modals:** Shown as a subtle tappable subtitle under the exercise name — never as a form field. Defaults to today or last-used date. Rarely changed by users.
- **Scroll lock on modals:** Toggle `overflow: hidden` on `.tabContent` via `html.modal-open` class. Do NOT use `touch-action: none` on the overlay — it doesn't work on iOS Safari. This lock is **mandatory, not cosmetic**: a `position: fixed` modal whose background stays scrollable desyncs its paint from its hit-test coordinates when the iOS keyboard opens (visual viewport shifts, layout viewport doesn't), so taps land a row low (#830). `useModal` now **owns this centrally** via a reference-counted lock (acquired in `open()`, released on `close()`/unmount), so any modal built on `useModal` is locked automatically — never re-add an ad-hoc `classList.toggle('modal-open', …)`. Pass `lockScroll: false` only when an ancestor modal already owns the lock for that surface (e.g. `SharePickerSheet` nested under `WorkoutCompleteView`/`PRBurst`).
- **Modal lifecycle via `useModal` (#831 / LIFT-878):** `useModal` is the single sanctioned owner of the three-part modal lifecycle — background-scroll lock (ref-counted `html.modal-open`), focus trap (composes `useFocusTrap`, `focusContainer` for text/number-first modals), and Escape-to-close (`onEscape`). Pass `onEscape` and useModal attaches ONE `window` keydown listener on `open()` and removes it on `close()`/unmount; never hand-roll `window.addEventListener('keydown', …)` or `classList.toggle('modal-open', …)` in a component again. A nested sheet whose ancestor already routes Escape to the topmost layer (e.g. `SharePickerSheet`) omits `onEscape` and passes `lockScroll: false`. **The rule is now enforced structurally** — `architecturalInvariants.test.ts` fails any `.ts`/`.vue` file outside `useModal.ts` that calls `classList.add/remove/toggle('modal-open', …)`. A behavioural test can only catch this in the one component it mounts; the two surviving copies (WorkoutTracker, migrated in #1082) lived through years of tests because nothing ever mounted two modal-owning components at once.
- **Driving `useModal` from state you don't own.** `useModal` owns `isOpen`, but WorkoutTracker's log sheet (`showModal`) and SettingsSheet's `modelValue` prop pre-date it and are read/written all over their components. Both bridge with a `watch(source, open => open ? modal.open() : modal.close())` rather than replacing the flag — assigning `showModal.value = true` directly would silently skip `open()` and the lock with it. SettingsSheet's bridge **must** be `{ immediate: true }`: App.vue mounts it with `v-if="settingsOpen"` (#955), so the sheet arrives already-open and the false→true transition never happens inside the component. WorkoutTracker holds **two** instances — `logModal` (lock + `.repMaxModal` focus trap + swipe gesture) and `childModalLock`, a lock-only instance covering the four prop-driven child modals (detail / edit / tag manager / gym manager), which run their own focus traps but take no lock of their own. Each contributes at most 1 to the shared count.
- **Component tests that mount modals must auto-unmount.** `useModal`'s `scrollLockCount` is module state shared across a whole test file. A wrapper left mounted with a modal open never releases its lock, so `html.modal-open` stays applied and every later lock assertion in that file passes vacuously. `WorkoutTracker.test.ts` and `SettingsSheet.test.ts` call `enableAutoUnmount(afterEach)` from `@vue/test-utils` for exactly this reason (it also cut WorkoutTracker's suite from ~69s to ~3s, since leaked mounts kept their watchers and timers alive).
- **Centered modals for iOS keyboard:** Do NOT add manual `paddingBottom` offsets for the keyboard. iOS natively adjusts the viewport for centered flex modals.

## Architecture Notes

- **Component layer convention.** `src/views/` holds container-level components that access stores directly (AuthScreen, OnboardingScreen, CalendarView, BodyweightTracker, ExerciseDetailModal). `src/components/` holds reusable, prop-driven presentational components (ExerciseGraph, MuscleGroupChart, SkeletonLoader, PRBurst, etc.). WorkoutTracker and SettingsSheet are planned to move to `src/views/` once their remaining sub-component extractions are complete; extracted so far as props+emits children: WorkoutTimeline, EditExerciseModal, TagManagerModal, ExercisePickerModal (from WorkoutTracker, alongside the earlier RestTimerContent/WorkoutCompleteView) and LegalSheet, ThemeStatsSheet (from SettingsSheet) — the log-set modal intentionally remains inline (settled pattern). When creating new top-level pages or screens that access stores, put them in `src/views/`. When creating reusable UI pieces that receive data via props, put them in `src/components/`.
- **Rest timer composables (LIFT-879).** `useRestTimerController` is a thin orchestrator that owns the countdown loop, pause/restart/stop, notification integration, and the disable/undo flow, and composes two single-responsibility helpers: `useRestTimerPresets` (duration presets + their localStorage persistence + add/remove/toggle) and `useRestTimerAlerts` (configurable warning-time state + persistence + the Web Audio warning/finish beeps and the AudioContext they run on). The controller re-exposes the preset/alert fields by delegation so `RestTimerContent.vue` still consumes a single `RestTimerController` surface (unchanged public interface). `useRestTimer` remains the settings-only flag holder (rest-timer enabled/autostart, bound to the preferences store) — distinct from the controller. The AudioContext is instance-scoped in `useRestTimerAlerts` (the controller is its sole consumer); beeps are no-ops until `ensureAudio()` runs on a user gesture.
- **Shared date helpers live in `src/lib/dates.ts`** (`localDateKey`, `todayISO`, `toLocalDateKey`, `setDayKey`, `formatShortDate`, `daysBetweenISO`). `localDateKey(d: Date)` is the single source of truth for turning a `Date` into a local `YYYY-MM-DD` key — use it instead of hand-rolling `getFullYear()/getMonth()/getDate()` string concatenation (that pattern drifted into ~8 divergent copies across views, components, composables, and lib before it was consolidated in #918; `todayISO` and `toLocalDateKey` are both built on it). The app's mental model is the LOCAL calendar day while the store persists UTC ISO timestamps — never derive a day key via `toISOString().slice(0, 10)`; it rolls evening dates to tomorrow in US timezones (this bug was independently fixed three times before the module existed). **Set/bodyweight dates carry two storage conventions and MUST be bucketed via `setDayKey` (#746):** UI-logged sets are written with `endOfDayISO(localDay)` → `…T23:59:ssZ` where the prefix IS the chosen local day (so `slice(0, 10)` is right and `toLocalDateKey` would shift +1 east of UTC), while the `logSet` no-date fallback and legacy data are real-time UTC instants (where `toLocalDateKey` is right and `slice(0, 10)` rolls Americas evenings to tomorrow). `setDayKey` detects the `23:59` end-of-day window (same string check as `sessionSummary.isEndOfDayJitter`) and routes accordingly — it is the single reconciliation point; never blanket-swap one derivation for the other. **`set.date` therefore answers "which day", never "what time" — that is `WorkoutSet.createdAt` (#846/#1288).** A UI-logged `date` carries no time of day at all, so anything needing a real instant (session duration, time-of-day, within-workout ordering) must read `createdAt`, falling back to `date` only when `date` is itself a real-time stamp. Deriving a *span* additionally requires the guard in `sessionSummary.sessionInstant`: a `createdAt` counts only when it lands on the local day the set is FILED under, because a back-dated set (or a pre-#846 set whose server `created_at` defaulted to its sync time) carries a real instant from another day and would report a 45-minute session as "3d 6h". Session duration read only `date` from #305 until #1288, so it was `'—'` for every user, on every session, the entire time. **A day-key test that does not pin `process.env.TZ` cannot fail** — CI runs UTC, where both derivations agree, which is how the same defect shipped four times (LIFT-1237 app-icon badge, LIFT-1247 store reads, #1291 session summary, #1293 weekly goal + training report) past suites whose fixtures happened to use only the one unaffected convention. Use the `withTZ` helper (`dates.test.ts`, `sessionSummaryDayKeys.test.ts`, `reportingDayKeys.test.ts`; Node honors a runtime `process.env.TZ` reassignment) and assert a zone on EACH side of UTC — an `Asia/Tokyo` case to catch the raw `toLocalDateKey`, and an `America/Los_Angeles` evening case — so the fix is pinned in both directions and cannot later swing to a blanket `slice(0, 10)`. `src/lib/storage.ts` provides `loadJSON` for guarded localStorage reads — corrupt storage must never throw into store init. **Element-level validation lives in `src/lib/parseGuards.ts` (LIFT-946):** `loadJSON`/`loadStoreData` only guard the *top-level* shape (parse + `Array.isArray`/`isPlainObject`), so a single corrupt element (a set missing `weight`, a recovery map holding strings, a tag array with a stray number) would still hydrate. `parseExercises`/`parseBodyweightEntries`/`parseStringArray`/`parseNumberRecord` validate every element at the localStorage boundary and drop (`logWarn`) the malformed ones — the workout/bodyweight `load()` and the workout secondary-tag hydration route through them. A missing/bad `estimated1RM` is *repaired* from weight×reps via Epley rather than dropping the set. This mirrors the per-field rigor `jsonColumns.ts` already applies to Supabase-JSON; the progression store's `migrateUnlockedThemes` and JSON-blob fields (`xpPerSet`/`streakHistory`/`bodyweightXPDates`) reuse the `jsonColumns` parsers so the two boundaries don't invent divergent checks. Rule: **no `JSON.parse` result may be cast to a domain type without passing through a guard.**
- **Local-first.** Pinia + localStorage is the source of truth. Supabase syncs in the background. The UI never waits on the network.
- **Store `$reset` = sign-out wipe (#1158).** `resetStores()` in `useAuth` calls `$reset()` on all four stores for BOTH manual sign-out and the automatic `SIGNED_OUT` teardown (LIFT-1133). Pinia's built-ins are wrong for this in both syntaxes: a setup store's built-in `$reset` throws in dev and silently NO-OPS in production, and an options store's built-in re-runs `state()` — which for factories that hydrate via `load()` (bodyweight, progression) "resets" straight back to the signed-out user's localStorage payload. Every store therefore defines its OWN `$reset` with wipe semantics: pure defaults in memory (never `load()`), `_userId` nulled before `_persist()` runs (so nothing enqueues against the dead session), and the cleared payload persisted (localStorage + IDB mirror). Skipping the persistence half re-arms two cross-account writes on a shared device: `migrateLocalStorageToSupabase` inserts leftover `bodyweight-entries` into the next empty account, and a fresh account's first progression fetch (PGRST116 → `_syncToSupabase`) pushes leftover in-memory XP/streaks into the new user's row; preferences' `init()` would likewise re-hydrate the previous user's coach profile from the surviving payload. Guarded by `signOutStateWipe.test.ts`, `workoutReset.test.ts`, and `signOutRealStores.test.ts` — all real Pinia under production NODE_ENV semantics (the failure is silent in prod builds; the store-mocking `useAuth.test.ts` can only prove `$reset` is *called*). When adding a store or a new piece of store state, extend its `$reset` and these tests in the same commit.
- **Account deletion covers every user-scoped table (LIFT-1225).** `deleteAccount` in `useAuth.ts` is the right-to-deletion path, and its correctness has two halves that failed independently. (1) **Resolved-vs-rejected:** supabase-js RESOLVES `{ data, error }` on RLS/FK/401 failures rather than rejecting, so `Promise.allSettled` + `filter(status === 'rejected')` counted a genuine server failure as success and wiped the device while the rows survived — the same trap the sync queue closed in LIFT-784. Every settled result is now failed when it rejected OR carries a truthy `.error`, and the throw happens BEFORE `localStorage.clear()`, so the caller's error UI fires with local data intact. (2) **Table coverage:** the list was written on 2026-04-05 and the AI-Coach migration added three more user-scoped tables on 2026-06-27 — `coach_usage`, `coach_usage_log`, `coach_consent`, holding the record that the user consented to health-data egress plus a per-request audit trail — which nothing ever added, so they outlived "delete my data" entirely. Those three go through the `delete_coach_data` SECURITY DEFINER RPC, and **the RPC is the only correct path, not a stylistic choice**: they have RLS on with SELECT-only policies, and an RLS-blocked `DELETE` is not an error in Postgres — it removes zero rows and answers `{ error: null }` — so a client `.from('coach_usage').delete()` would pass the check in (1) and report success having deleted nothing. The RPC returns the same `{ data, error }` shape, so it joins the same batch under the same assertion. Coverage is **derived, not enumerated**: `architecturalInvariants.test.ts` reads every `user_id`-scoped table out of the migrations and every table `deleteAccount` reaches — direct `.from().delete()`, an RPC's own `delete from` statements, or a transitive `on delete cascade` — and fails when one is uncovered. A hardcoded list would only ever pin the tables that existed when it was written, which is exactly how the coach tables slipped through. **Adding a `user_id`-scoped table means giving it a deletion path in the same commit**; when the client has no DELETE policy, that path is an RPC. (3) **Both server stages are skipped entirely for a guest (LIFT-1301).** A local-only guest (LIFT-1083) is a full user to the UI — `SettingsSheet` carried no `isGuest` branch at all until LIFT-1310 — but its identity is the sentinel string `'guest-local'`, which is truthy and so passed the `supabase && userId` gate. Every filter then compared a `uuid` column against a non-UUID (400 / SQLSTATE 22P02), and by (1) that resolved error correctly aborts *before* `localStorage.clear()` — so the one user who needs no network to honour deletion was the only one who could never complete it, deterministically, with no in-app way to erase their own device. The gate is `!isGuest.value`, matching every other guest branch (`App.vue`'s `handleSignOut`, the `SIGNED_OUT` teardown) rather than testing the sentinel, which is a symptom of the flag. Deletion also ends guest mode explicitly via `clearGuestFlag()` — `localStorage.clear()` drops the persisted key but not the in-memory ref, and the end state (back at the auth gate, nothing carried over) should be a decision, not a side effect of a call that never names the key. **A regression test here must model the `uuid` column type**: the shared `mockDelete` fake resolves `{ error: null }` for any id, which is why a guest path that failed on every real device passed every test that had ever run it.
- **Account deletion deletes the ACCOUNT (#1299).** `deleteAccount` in `useAuth` runs three stages in a fixed order, and the order is load-bearing: (1) per-table deletes of the user's application rows in one `Promise.allSettled` batch; (2) `supabase.rpc('delete_user_account')` — the `auth.users` row itself; (3) only then the local wipe (`localStorage.clear()`, IndexedDB, `signOut()`). Stage 2 is a SECOND await rather than another entry in the batch because deleting the auth user **cascades** through every `user_id ... on delete cascade` FK and is unrecoverable — run last, a failure anywhere earlier aborts while the account still exists; run first or concurrently, a later failure aborts having already destroyed it. Every stage asserts on the **resolved** `{ error }`, not just a rejected promise (LIFT-1225), and throws BEFORE the local wipe so a partial server-side deletion never leaves the device cleared while rows survive. Stage 2's failure message is deliberately distinct ("Your data was deleted, but your sign-in could not be removed") — by then the rows really are gone, so a generic "failed to delete" would read as "nothing happened, Cancel is safe". Until #1299, stage 2 did not exist: the app deleted every row and signed out, leaving the user's email, OAuth identity linkage and sign-in metadata alive indefinitely with no in-app way to remove them, under a button labelled "Delete Account" — a copy lie and an App Store account-deletion-review blocker. The browser holds the anon key and cannot reach `auth.admin`, so a `SECURITY DEFINER` RPC deriving the user from `auth.uid()` (the same shape `delete_coach_data` established) is the client's only path. **Any new user-scoped table must be added to stage 1** — the auth-user cascade in stage 2 is a backstop, not the contract, since stage 1 is what proves the deletion succeeded. `.rpc()` names are plain strings, so `architecturalInvariants.test.ts` fails any `supabase.rpc('…')` in `src/` with no matching `create [or replace] function` in `supabase/migrations` (a missing function is a *resolved* `{ error: PGRST202 }`, and LIFT-1169's migrate-db/Vercel race makes the code-ahead-of-schema window real). `supabaseIntegration.test.ts` signs in as a real password user and calls the RPC against a live Postgres — the only place that can catch a wrong function owner or missing grant on `auth.users`, which fails at CALL time and is invisible to every fake-Supabase test.
- **Guest-facing copy forks on `isGuest`, never on `user` (LIFT-1310).** A local-only guest (LIFT-1083) has no account, and `continueAsGuest` sets `user` to the truthy sentinel `{ id: 'guest-local', email: '' }` — so a `user ?` check reads as "signed in" for them, and every account-shaped string in `SettingsSheet` named a concept they do not have. The *behaviour* had already forked (App.vue's `handleSignOut` → `exitGuestMode()`, LIFT-1301's server-stage skip); only the words hadn't, and two of them were affirmatively false. The delete dialog's "You will not be able to sign back in" arrived with #1299 and is true only of a real account — a guest lands on the auth gate afterwards and can tap "Continue as guest" again immediately. The Data group's "Synced over encrypted HTTPS" told a lifter with no backup that they had one, while App.vue's own guest banner said "saved on this device only" one tab away. The guest variants are **Exit Guest Mode** (confirm: "Exit guest mode? Your workouts stay on this device.") and **Delete All Data**, with the account/sign-in clause dropped from the description. The DELETE-to-confirm gate is deliberately unchanged for a guest: that dialog is the only way they can erase their device and it is exactly as irreversible, so softer copy must not become a softer confirmation. The Danger Zone row and the dialog title read from ONE computed (`deleteActionLabel`) because the title is the alertdialog's accessible name — a drift would announce a different action than the one just tapped. **A new guest-visible string branches on `isGuest`, and a test for it must set BOTH refs** (a truthy `user` AND `isGuest`): a guest fixture that leaves `user` null passes off the falsy `user` and proves nothing, which is the shape that hid this — `SettingsSheet.test.ts` mounted with `user: ref(null)` and had never once mounted as a guest, the same blind spot that let LIFT-1301 ship.
- **Settings ownership (LIFT-821 / LIFT-1177).** The `preferences` store is the single source of truth for synced appearance/behavior settings. `useWeightUnit`, `useRestTimer`, **and now `useTheme`** are thin accessors whose refs are **writable computeds bound to the store** (`weightUnit`, `restTimerEnabled`, `restTimerAutoStart`, `theme`/`currentTheme`, `colorMode`) — none holds a module-scope ref or touches localStorage directly, so a change made via the composable and one made via the store can't diverge. The old one-shot `syncSettingsWithComposables()` bridge (which pushed store→ref exactly once, then watched ref→store) is **gone** — it silently dropped any direct store mutation (cross-tab `_reloadFromStorage`, the Supabase override during `init()`), leaving the DOM/UI stale. Two pieces make the store the true single owner across every auth state: (1) the store **hydrates its local settings in the state factory** (`loadLocalSettings()`, mirroring bodyweight/workout) so it holds the user's real values the instant it is first touched — before `init()` resolves and even for a local-only guest who never calls `init()`; (2) `connectThemeStore()` (called once from App.vue) makes the DOM a **pure function of the store** — it applies `prefs.theme`/`prefs.colorMode` on connect and watches them, so every change from any source reaches the DOM. `initTheme` in `main.ts` still runs the **pre-Pinia FOUC bootstrap** (reads `app-theme`/`app-mode` from localStorage, applies to DOM, migrates the theme id, forces glass on) but no longer owns any reactive ref or watcher. `_persist` still writes the legacy individual keys (`app-theme`, `app-mode`, `weight-unit`, `rest-timer`, `rest-timer-autostart`) for FOUC/migration, from the single store owner in one atomic write. This closes the open tail of LIFT-821. **The persisted payload is defined exactly once, in `_buildPayload()` (LIFT-1243)** — the write-side twin of `_applyPreferences`. `_persistLocal()` writes it to every LOCAL sink (primary key + IDB mirror + cross-tab broadcast + FOUC mirror keys) and `_persist()` adds the debounced remote upsert; `init()` calls `_persistLocal()` after adopting a remote row, deliberately NOT `_persist()` (echoing the just-fetched row back at launch would burn a write and open a window to clobber another device's concurrent change). `init()` previously hand-built a second copy of the payload and wrote it straight to localStorage, which skipped the FOUC keys — so a remote theme adopted at sign-in flashed the *previous* theme on every later cold start, and skipped the cross-tab broadcast so other open tabs never saw the adopted settings. **A new synced preference goes in `_buildPayload` and `_applyPreferences`, and nowhere else.**

- **Fresh-identity child bindings (#963).** The workout store holds `exercises` in a `shallowRef` and mutates entries IN PLACE, signalling via `triggerRef` — the array's identity never changes. - **Bar weight lives in the DISPLAY unit (LIFT-1211 / LIFT-1223).** The whole plate subsystem — the denominations (`KG_PLATES`/`LBS_PLATES`), `Exercise.barWeight`, and the plate card's total — operates in the user's display unit: kg users stack kg plates on a kg bar. Canonical lbs cross that boundary only via `displayWeight()` on the way in and `toLbs()` at set-save time. Two consequences, and each one has already shipped broken. (1) **A stored bar must be converted when the unit toggles**, or the raw number is silently reinterpreted (a 20 kg bar becomes a 20 lb bar): `preferences.setWeightUnit` is the sole user-initiated toggle path and calls `workout.convertBarWeightsForUnitChange`, which routes each explicit value through `convertBarWeight` in `plateCalculator.ts`. Exercises with no explicit bar are skipped (they fall through to the default, which is already unit-aware) so a toggle never adopts a sample exercise just to stamp one. (2) **Every fallback for an exercise with no stored bar must be unit-aware too**, which is `defaultBarWeight(unit)` in `plateCalculator.ts` — the single source of truth, returning the same standard bars `convertBarWeight` snaps to, so a converted bar and a defaulted one can't drift apart. - **Strength baseline mode (#1272).** What "your best" means is a **user preference**, because the right answer changes with the phase of training. Bulking, the lifetime peak IS the target; cutting, it recedes every week, so a peak-anchored baseline silences PR detection and collapses every set into the linear working zone — the app stops rewarding a lifter through the hardest part of the year. `src/lib/strengthBaseline.ts` (pure, clock-free — `todayKey` is a parameter, like `buildSessionPlan`) adds `strengthBaselineMode: 'lifetime' | 'recent'` (default `lifetime`, so existing users see no change) plus `recentBaselineWeeks` (default 8, clamped [2, 26], stepped by 2 in Settings). **The modes are not two measurement paths — they resolve to the ONE `sinceDate` day key the app already threads everywhere** (`getExercisePR`, `calculateBest1RM`, `filterSetsSinceBaseline`), so display badges, the PR burst, the intensity-lens anchor, the to-beat card, and `scoreSet`'s XP calibration all move together by construction. A parallel "recent best" lookup beside the existing one would have meant two answers to "what's my max?" and a second thing for every future PR consumer to get wrong. `resolveStrengthBaseline` is that single resolution point: lifetime → the manual anchor verbatim; recent → the LATER of the anchor and `todayKey − weeks × 7` (both are floors, so the later one is the tighter window — a block started three weeks ago still shadows an eight-week window; one from last year does not). `usePRBaseline().prBaselineDate` is now the **resolved** value and is what every consumer must read; the raw stored date is exposed separately as `prBaselineAnchor`, for the Settings input alone. XP calibration therefore needs no mode-aware branch — equaling recent work is a tie (2×) and edging it is a PR (3×) purely because `calculateBest1RM` was handed a nearer baseline. There is deliberately **no** mode-specific XP multiplier; that would fork the curve for the same reason a second lookup would fork the baseline. `MAX_RECENT_BASELINE_WEEKS` (26) is capped at `XP_CONFIG.best1RMWindowMonths` so recent mode can only ever narrow the window it exists to tighten. `sanitizeRecentBaselineWeeks` is stricter than its `sanitizeIntensityMaxReps` sibling on purpose: `Number(null)`/`Number([])` are both `0`, so a coerce-then-clamp guard would turn a corrupt or absent field into the 2-week **minimum** — the narrowest baseline in the app, silently applied — hence only a real finite number is accepted. An empty recent window behaves exactly as an empty manual block already does (no established best → `new_exercise` zone, suggestions hidden until something is logged); that is the settled precedent for this plumbing, not a new edge case. The ledger invariant is unchanged: switching modes never rewrites awarded XP or stored `isPR` flags. WorkoutTracker's copy follows the mode (`recent max` / `Recent best` / `To Beat Your Recent Best` / `New recent best!`) so a recent best is never misreported as a lifetime PR. Do NOT add authored bulk/cut phases, or couple this to the bodyweight goal direction, without explicit request — the issue's second alternative was deliberately deferred.
- **Sets-per-day index (LIFT-1237).** `store.setsLoggedOn(dayKey)` is the single answer to "how many sets on this local day?" — it backs WorkoutTracker's always-visible "Finish workout" affordance and App.vue's unfinished-workout app-icon badge. The index is a plain closure `Map<dayKey, count>`, deliberately **not** a ref — reads take their reactive dependency on `exercises` itself (every mutation already triggers it), so the cache can be built or repaired from inside a computed without a ref's self-invalidating write. `logSet`/`updateSet`/`deleteSet`/`restoreSet` maintain it incrementally via `_adjustDayCount`; the three wholesale replacements of `exercises` (`_reloadFromStorage`, `_fetchFromSupabase`, `$reset`) call `_invalidateDayCounts`. **Correctness does not depend on hooking every future mutation site:** each read first compares a checksum — the summed `sets.length` of every exercise, O(exercises) — against the total the index was built from, so any unhooked add/remove path (e.g. `deleteExercise`) forces exactly one rebuild instead of miscounting forever. - **Bodyweight-loaded exercises (LIFT-834).** Calisthenic lifts (pull-ups, dips, weighted chins) carry an `Exercise.bodyweightLoaded` flag: the `weight` field then means the *added* plate/belt weight, and the lifter's bodyweight is folded into the effective load for volume + e1RM (so "+25" counts as ~185 and a pure-bodyweight rep at added=0 still scores). `src/lib/bodyweightLoad.ts` owns the offset between the two weight spaces — ADDED (`set.weight`, and what the log sheet's weight field means) and EFFECTIVE (added + bodyweight, what `estimated1RM`, volume, and every PR comparison are measured in). `bodyweightFold(exercise, bodyweight)` is the only place the flag is consulted; `effectiveSetWeight(set, exercise)` adds it and `addedWeightFromEffective(effective, exercise, bodyweight)` subtracts it, so the fold and its inverse sit adjacent and cannot disagree (the structural argument LIFT-1312 made for `platesToWeight`/`weightToPlates`). So a pure-bodyweight pull-up day charted ~5,550 in the exercise graph and **0** in the calendar summary for the same sets — two answers from the same store, one screen apart. Two shapes recur and are worth recognizing: a loop that **flattens** its rows away from the exercise (`trainingReport`'s `SetWithExercise`, `themeStats`' `setLookup`) must resolve the effective weight where the exercise is still in scope — both now carry an `effectiveWeight` field — and a report that also converts units must fold **in lbs first**, since `set.bodyweight` is stored in lbs like `set.weight` and converting first adds a pound count to a kilo count (the LIFT-1315 mixed-space failure). `architecturalInvariants.test.ts` now fails any `.weight * .reps` product in `src/` outside `bodyweightLoad.ts`, so a NEW volume sum cannot forget the fold; a per-file test would only ever pin the sites that existed when it was written, which is exactly how these five survived LIFT-834. **Reading an e1RM back OUT is a THIRD boundary, and it was missed for a year (#1328).** The log sheet inverts a stored e1RM to answer "what should I load next?", and that answer lands in the weight field — i.e. in ADDED space — so every 1RM surface there (live estimate, PR badge, to-beat card, `prTargetReps`, the intensity-lens anchor, the XP preview) has to cross the offset, in the right direction. It crossed none of them: `WorkoutTracker.vue` did not import `effectiveSetWeight` at all, so a 160 lb lifter's "+25 × 5" pull-up read as a ~29 lb estimated 1RM against a stored PR of ~216 (the badge could never fire), and the *tappable* to-beat card offered ~186 as an ADDED weight — which folds a second time on save (~404 e1RM), wins the PR, fires the burst, pays PR-multiplier XP, and re-anchors every later suggestion off the inflated number. The floor now lives once, in `isLoggableWeight(weight, exercise)` beside the fold, and is keyed on the **flag, not the fold** — `bodyweightFold` is also 0 for a lifter who has never weighed in, and Save must not silently depend on a number entered in another tab. The surfaces that need a real load to say anything gate on the FOLDED total instead (`typedLoadLbs`), because "how many reps at nothing beats your PR" divides by zero and rendered an Infinity rep count. **Empty stays distinct from an explicit 0** (`weight` is `null` for an untouched field) — that gap is what keeps the "what should I add?" card on screen, and the card is now tappable, filling 0, since #1328's reason for it being informational-only ("a set needs a positive weight to save") is exactly what this removed. - **Paged collection reads (#1152).** PostgREST caps EVERY response at the project's `max_rows` (1000, `supabase/config.toml`) and signals the truncation nowhere — no error, no flag, just a short array indistinguishable from "that's all the rows." This shipped broken: the unpaged `sets` read sorted `created_at` ASCENDING, so an account past the cap hydrated its OLDEST 1000 sets and the app reported that training stopped on the day set #1000 was written (1454 sets on the server, five weeks of history invisible, "4 weeks since your last workout" banner on top). - **Fetch-path dedup is two passes with deliberately different key granularity (LIFT-1332).** `_fetchFromSupabase` runs `deduplicateByName` (collapses two exercise rows sharing a name but holding different UUIDs — the cross-device case) and then `deduplicateSets` over each merged list. Both are **strictly local**: the client has no authority to push dedup-derived deletes, per the 2026-04-12 SEV1 that destroyed user data doing exactly that. The split of responsibility is the invariant: `deduplicateByName` merges **by set id only**, and `deduplicateSets` is the sole content-based pass, keyed on the **FULL ISO timestamp**. `deduplicateByName` additionally gated on a day-level `day|weight|reps` content key from 2026-04-06 to LIFT-1332, and that key lived in a `Set` — **count-blind**, so it admitted at most ONE set per tuple and straight-set programming (5x5, 3x10) collided with itself by construction: a duplicate row's whole day of work merged in as a single set, or as nothing. The case the coarse key was reaching for is a re-run of `migrateLocalStorageToSupabase`, which mints fresh set UUIDs but copies `date` **verbatim** — so those copies collide on the full timestamp and the second pass already catches them, while `endOfDayISO`'s seconds/ms jitter keeps genuine same-day repeats distinct. **Never re-introduce a day-level content key here**; if a future artifact escapes both passes, it needs a count-aware rule, not a count-blind one. Guarded by `workoutNameDedup.test.ts` (whole fetch pipeline, including the localStorage commit) and the `deduplicateByName` block in `workout.test.ts` — which for years asserted only which *exercises* survived, never how many sets came across, which is why this sat undetected.
- **A per-set field is synced or it is preserved — never neither (#1357).** `mergeEntities` resolves exercises by last-write-wins and picks one **wholesale, sets and all**; the union that follows only adds sets the winner is MISSING. So when the REMOTE row wins — a rename or re-tag on another device, or a replayed journal entry bumping `updated_at`, is enough — every set present on both sides is replaced by the server's copy of itself. That is lossless for every column `sets` has, and silent data loss for the two `WorkoutSet` fields it does not: `rpe` (#617) and `bodyweight` (LIFT-834) are local-only, so the adopted copy carried `undefined` where the user's annotation was. Restore **fills only what the merged set lacks**, so the day one of these fields gains a column, remote-wins keeps meaning remote-wins (including a deliberate clear). Placing it after dedup rather than inside the union loop is deliberate: it then covers every set about to be committed, not just the ones LWW touched. The field list is **derived, not enumerated** — `architecturalInvariants.test.ts` reads every `WorkoutSet` field from the store and every field `mapRemoteSet` reads back, and fails unless the difference is exactly `LOCAL_ONLY_SET_FIELDS`, in both directions. **Adding an optional `WorkoutSet` field means giving it a `sets` column or adding it to that list in the same commit.** Nothing caught the original because every fetch-path fixture seeded sets through plain `logSet` with none of the optional fields set, so the two fields that cannot round-trip were never *present* when a remote row won: a regression test here must seed local state with them and assert on the committed AND persisted state.

- **A Supabase mutation does not reject when you are offline (LIFT-1321).** postgrest-js catches the fetch rejection internally and **RESOLVES** `{ error: { message: 'TypeError: Failed to fetch', code: '' }, status: 0 }` (verified in `@supabase/postgrest-js` dist — the `shouldThrowOnError === false` branch); it likewise resolves `{ error }` for RLS denials, constraint violations and 5xx. So **any code that decides success by "the promise didn't reject" is wrong** — the trap `deleteAccount` hit in LIFT-1225 and the write queue hit here. `SyncQueue._settleFailure` treats ANY truthy resolved `error` as a failure; it previously excepted only auth errors (the narrow LIFT-784 fix), so an offline flush one second after a logged set cleared the retry counter, **deleted the durable journal entry**, and reported `'synced'` — making the entire retry/backoff + journal-retention machinery unreachable for the app's most common failure class. `isRetryableSyncFailure` (in `syncStatus.ts`, beside `classifySyncError`) then decides only whether to *retry in-session*: auth / network / `status: 0` / 5xx / 408 / 429 retry; a 4xx the server understood and refused (RLS `42501`, unique `23505`, schema-cache `PGRST204`) leaves the queue after ONE attempt instead of burning five identical round-trips. **Retryability is not durability** — the journal is retained either way (LIFT-1229), which is what turns the LIFT-1169 code-ahead-of-schema 400 into a clean upsert on the launch after the migration lands. A failed batch while `navigator.onLine === false` reports `'offline'`, not `'error'`, so the flush can't contradict the connectivity App.vue tracks on the same ref. **The suite could not have caught this**: every sync test modelled offline as `Promise.reject`, so all 3874 passed identically before and after the fix. `createFakeSupabase` now has a `'networkError'` mode resolving the real envelope (`FAKE_NETWORK_ERROR_RESULT`) — use it, not `'reject'`, to mean "offline", the same fake-fidelity rule as the `max_rows` cap. The retry budget no longer burns against a radio the browser knows is dead — see the offline-park bullet below (LIFT-1322).
- **An offline write is parked, not attempted, and recovers on reconnect (LIFT-1322).** Five exponential-backoff retries exhaust in ~31 seconds, so once resolved network errors became real failures (LIFT-1321) *any* offline stretch longer than half a minute — i.e. every real one — dropped the in-memory op and stranded its retained journal entry until the **next cold start**: `rehydrate()` is called once, from `useAuth.initStores`, and `useSyncRecovery`'s `online` trigger dutifully flushed a queue that had already been emptied. A lifter who trained through a dead spot and walked back into signal kept stale server state for the rest of the session, silently (the local-first UI shows the write as saved either way). Two halves, and **both are needed because they cover different failure modes**: (1) `flush()` returns early while `isOffline()`, keeping the queue intact and counting no attempt — but that only helps when the browser KNOWS it is offline, and `navigator.onLine` is `true` on a dead uplink (captive portal, associated-but-dead gym wifi) more often than not, which is why the gate reads `=== false` and never treats `true` as permission; (2) `syncQueue.replayJournal()` rebuilds ops from the in-memory journal for keys that aren't already pending, and `useSyncRecovery.run()` calls it **before** the flush, so the existing write-before-read ordering carries the recovered backlog too. A parked queue arms its own one-shot `online` listener rather than relying on `useSyncRecovery` — that one is rate-limited to one run per `REFETCH_COOLDOWN_MS`, so an `online` event arriving just after a resume re-fetch is dropped outright and the writes would stay parked all session. `replayJournal` **skips keys whose last failure was non-retryable**: their entry is still retained for the next launch (LIFT-1229 — the window where a migration can land, LIFT-1169), but re-issuing a refusal on every reconnect and foreground resume can only reproduce it while logging a fresh Sentry error each time. It **does** clear `_attemptMap` for the keys it re-arms — a replay is provoked by an external "the world changed" signal, which is precisely what a fresh backoff ladder is for; that is scoped to the replay path only, leaving the plain-`enqueue` budget carry-over as LIFT-1326.
- **Durable write queue.** Writes enqueued via `syncQueue` can carry a serializable `SyncDescriptor` (upsert/update only — idempotent for safe replay). Descriptors are journaled to IndexedDB so pending offline writes survive a tab close and are replayed on next launch via `syncQueue.rehydrate()` (called from `useAuth.initStores`). `SyncDescriptor.table` is `keyof PublicTables` (not `string`) and every payload column is typed against that table's generated Insert/Update/Row shape (LIFT-948), so a stale/misspelled column fails typechecking at the producer; `isReplayableDescriptor` + the `REPLAYABLE_COLUMNS` allowlist re-validate table + columns at runtime on rehydrate since the journal lives in user-writable IndexedDB (LIFT-785). **That allowlist MUST stay in lockstep with the upsert producers (LIFT-1039).** `isAllowedColumnMap` is all-or-nothing — one un-allowlisted key rejects the WHOLE descriptor — so a column added to `_buildExerciseUpsert` without a matching entry silently discards *every* journaled exercise write on rehydrate, defeating the durable queue for the exact offline case it exists for. The failure is invisible (a `logWarn`, no user-facing error), and it drifted three times on `exercises`: `equipment` (#931) + `gyms` (#961), then `plate_count_mode` (LIFT-783), then `notes` (#619) + `bodyweight_loaded` (LIFT-834). A hardcoded-row test cannot catch this — it only ever pins the columns that existed when it was written, which is how the last two slipped past the LIFT-1039 regression test. `architecturalInvariants.test.ts` now derives the producers' column sets from source and fails if any is missing from the allowlist, so **adding an always-send column to a producer means adding it to `REPLAYABLE_COLUMNS` in the same commit**. The persisted journal is a versioned envelope `{ version, entries }` stamped with `JOURNAL_SCHEMA_VERSION` (LIFT-1132): rehydrate discards a journal whose version doesn't match (a breaking migration since it was written) rather than replay stale column names into silent PostgREST failures — bump the constant only for a breaking descriptor change (column rename/drop, changed match shape), never for an additive column. A legacy bare-array journal (pre-LIFT-1132) is treated as the current generation so the upgrade that introduced versioning doesn't drop in-flight writes. The journal is wiped on sign-out so a shared device never replays the previous user's writes. **A descriptor is mandatory, not optional (LIFT-1239):** the journal only engages when one is passed, so for a long time only `workout.ts` supplied them and a bodyweight entry / XP credit / settings change made offline was lost outright on a close before the 1s flush — and had no durable record to retain when its retries were exhausted (LIFT-1229). All four stores now journal (`bodyweight_entries`, `user_preferences`, `user_progression` joined `sets`/`exercises` in `REPLAYABLE_COLUMNS`), enforced structurally by `architecturalInvariants.test.ts`, which fails any `syncQueue.enqueue`/`enqueueDelete` under `src/stores/` that omits the descriptor without a `durable-journal-exempt` marker on the line above. The single exemption is `bodyweight.clearAll`: its match is unbounded, a descriptor can only express `eq` filters (so `.is('deleted_at', null)` would be lost), and replaying a wipe next launch would destroy entries logged on another device since. Because `user_preferences` upserts on `unique(user_id)` rather than its surrogate `id` PK, `executeDescriptor` applies the `UPSERT_CONFLICT_TARGET` map — kept client-side, never on the descriptor, so a tampered journal can't choose the conflict column. Every replayed key matches its live counterpart, so a fresher write supersedes a stale replay instead of racing it — for bodyweight (`_fetchFromSupabase`'s reconciliation pushes) and progression (the `_syncToSupabase` after its union merge) that happens on the same launch. Preferences is the exception: its `init()` adopts the remote row by writing localStorage directly rather than through `_persist()`, so a replayed settings change lands on the server while the UI shows the remote value, and only appears on the launch after. That flap follows from the store's remote-wins-on-init rule (a whole-blob LWW with no per-field timestamps) and converges on the user's most recent intent. Reconciliation in `_fetchFromSupabase` is the second line of defense: it re-pushes local sets missing from the server even on remote-winning exercises (union-then-push). The Background Sync API is intentionally not used — iOS/WKWebView, the App Store target, lacks it.
- **The IndexedDB backup is ONE connection, and it must be willing to give it up (LIFT-1356).** `durableStorage.ts` holds a single cached `IDBDatabase` for the life of the tab, backing both the localStorage mirror and the durable sync journal. `openDB` is **single-flight**: four stores persist independently, so several `backupToIDB` calls routinely land in the same tick, and each used to open its OWN connection while the last `onsuccess` overwrote the cache — leaking handles `closeDB()` cannot close. That is not a tidiness point, because **an open connection blocks `indexedDB.deleteDatabase()` indefinitely** and account deletion is the only thing that erases the backup and the journal from disk. Three consequences. (1) Every connection carries `onversionchange` (close, then drop the cache), so a delete issued by ANOTHER Lift tab is not blocked by this one; without it "Delete Account" left the previous user's workout backup and sync journal on a shared device while the UI reported success. (2) Every connection carries `onclose`, AND `withDB` reopens once on `InvalidStateError` — a browser-forced close (WebKit storage pressure, or another tab's delete landing) left the cache non-null and dead, so every later `transaction()` threw into a swallowed `catch` and the backup plus the offline journal became permanent silent no-ops for the rest of the session, with no signal anywhere. The event handler alone is not enough: it is dispatched as a task, and the throw is synchronous. (3) `deleteAllIDB` **clears the store's contents BEFORE deleting the database** — a transaction is never blocked by another connection while a delete is, so even a genuinely blocked wipe (a tab still running an older build) leaves nothing behind. `deleteDatabaseByName` AWAITS the request and reports `deleted` / `blocked` / `error`; the request used to be fired and dropped, which is exactly why a wipe that never happened was indistinguishable from one that did. It settles on `blocked` rather than hanging on a tab the user may never close, and `deleteAccount` **reports rather than throws** at that point — by then the server rows and the `auth.users` row are already gone (#1299), so "deletion failed" would be a lie in the other direction. `clearIDB` likewise resolves only once its transaction has COMMITTED, since `devClearAll` reloads the page on the next line. **A test here must run against `fake-indexeddb`**, which models `versionchange`, `blocked` and closed-connection errors faithfully — a hand-rolled double cannot express "pending", which is the whole of the defect (the same fake-fidelity rule as `createFakeSupabase`'s `max_rows` cap and its `networkError` mode).
- **Share flow (LIFT-880).** Both share surfaces run the same shape of pipeline — an ordered list of tiers (native system sheet → Web Share API → a local fallback), guarded against re-entrancy, never throwing on user-cancel, surfacing failures as a typed outcome. `src/composables/useShareFlow.ts` owns everything they share: the `ShareResult` union (one type across both surfaces), the `isSharing`/`lastError` refs, the `run(attempts)` sequencer (first terminal result wins; all-fall-through → `unavailable`; thrown → `error`), and the `isShareCancellation` detector (DOMException `AbortError` OR a message mentioning cancel/abort). `useAppShare` supplies text/URL tiers (native Capacitor share → Web Share → clipboard copy); `useWorkoutShare` supplies an image-Blob tier (render offscreen → Web Share files → download) and maps the terminal result onto the share funnel analytics (#712) via a single `logOutcome`. Add new share surfaces on top of `useShareFlow`, not by re-implementing the sequencing.
- **Bodyweight Health export (#1159).** The Weight-tab hero carries a share-icon button (`.bwExportBtn`, entries-only) that exports a `Date,Weight` CSV for Apple Health import (Health has no native CSV import; the Health CSV Importer app and Shortcuts "Log Health Sample" automations consume exactly this shape). `src/lib/bodyweightExport.ts` is pure: `dailyLatestBodyweight` (latest entry per `setDayKey` day, ascending — the SAME function the tracker chart renders, so file always matches chart) + `buildBodyweightCsv` (rows converted with `toDisplayWeight`, which must mirror `useWeightUnit.displayWeight` rounding) + `bodyweightCsvFilename` (unit lives in the filename — `lift-bodyweight-lbs-…csv` — because the columns stay strictly `Date,Weight` for importer compatibility). `useBodyweightExport` is a `useShareFlow` surface: Web Share file tier (iOS share sheet → Files/AirDrop/importer apps) → `downloadBlob` fallback; `downloadBlob` now lives once in `dataExport.ts` (SettingsSheet's export and `useWorkoutShare`'s card download were consolidated onto it).
- **Session health / token expiry (LIFT-784).** The Supabase client is created with explicit `auth` options (`persistSession`, `autoRefreshToken`, `detectSessionInUrl`). Because supabase-js's visibility-driven refresh timer is unreliable in WKWebView/Capacitor on resume from background, `useAuth.setupSessionRefreshLifecycle` re-arms `startAutoRefresh()`/`stopAutoRefresh()` on `visibilitychange` + `focus` + `pageshow`. `src/lib/sessionHealth.ts` distinguishes a 401/JWT-expiry (`isAuthError` — checks status/`PGRST301`/`PGRST303`/message) from an offline error, and `ensureFreshSession()` does a single-flight `refreshSession()` so a wave of stale-token writes triggers ONE refresh. The write path (`syncQueue.flush`) treats a *resolved* auth error — not just a rejection — as a retryable failure (a 401 resolves `{ error }`, so it used to be silently dropped as success) and fires `ensureFreshSession()` once per batch; read paths (`_fetchFromSupabase`, in **all four** stores) do the same. If refresh fails, the reactive `authNeedsReauth` flag drives a non-blocking "Session expired — sign in again" banner in `App.vue`; it clears on the `TOKEN_REFRESHED`/`SIGNED_IN` auth event. **Every failure branch of a store read must offer that recovery, and the count is enforced structurally (LIFT-1179).** The four `_fetchFromSupabase` bodies are four hand-written copies of one contract — report (`reportFetchError`), classify (`lastSyncError = classifySyncError(…)`), refresh on `isAuthError`, clear `syncing` in a `finally` — and three of them had drifted: `preferences` carried no auth branch at all, and `workout`/`bodyweight` had one on the resolved `{ error }` path but not in their `catch`. Nothing caught it because **no store fetches alone**: `initStores` and `useSyncRecovery` fan all four out under `Promise.allSettled`, and a token expiry hits all four at once, so some sibling always raised the refresh and the gap was masked by the fan-out rather than absent. A store that ever reads on its own would record `lastSyncError = 'auth'`, light the generic red indicator, and never refresh the token, raise the banner, or bump `sessionRecoveryTick` — i.e. the app's only *actionable* sync failure would present as its most generic one. `architecturalInvariants.test.ts` therefore **derives** the rule from the store sources: it extracts every `_fetchFromSupabase` (both store syntaxes, comments stripped) and requires `ensureFreshSession` and `classifySyncError` counts to EQUAL the `reportFetchError` count. Equality, not "at least one" — two failure branches with one refresh is exactly the shape that shipped. Note the two error shapes are NOT interchangeable and a fix must cover both: postgrest-js RESOLVES `{ error }` for a 401 (LIFT-1321) while a token problem raised inside the client rejects, which is why `isAuthError` normalizes both and why `storeFetchAuthRecovery.test.ts` runs every store against each shape **in isolation** — the only arrangement in which the defect is visible.
- **Read-path recovery (LIFT-1226).** Writes were assumed to self-heal (queue retries + durable journal; they only did within the ~31s retry budget — see LIFT-1322 above); READS had no equivalent, so a store's `_fetchFromSupabase` failure was terminal for the session — an offline cold start, a network blip, or a token expiry left the app on local-only data, with the reconciliation pushes that live *inside* `_fetchFromSupabase` parked too, until a full relaunch. `src/composables/useSyncRecovery.ts` is the single write-replay + re-fetch entry point: `refetchAllStores(trigger)` replays the durable journal (LIFT-1322), flushes the sync queue, and THEN reads all four stores (`Promise.allSettled`). **Order matters** — every store read is remote-wins for the fields it carries, so fetching ahead of a queued offline edit would paint the stale server value back over it. `setupSyncRecovery()` (called once from App.vue, torn down on unmount) drives it from three signals: `online`, foreground resume (`visibilitychange` + `focus`, doubled up for WKWebView like `setupSessionRefreshLifecycle`), and `sessionRecoveryTick`. That tick is a **monotonic counter in `sessionHealth`**, not a watcher on `authNeedsReauth`: the common recovery is 401 → refresh → success, in which the flag is never raised and so has no true→false edge — the tick bumps on a successful `ensureFreshSession()` and on a `clearReauthFlag()` that actually clears a raised flag (never on a routine TOKEN_REFRESHED). Triggers are single-flight and rate-limited to one run per `REFETCH_COOLDOWN_MS` (20s), since a resume fires two events and a flaky link re-fires `online`; a blocked `session-recovered` trigger is the one exception — it schedules a single trailing re-run instead of being dropped, because it *always* lands inside the cooldown of the very read that 401'd. Preferences' remote read was extracted out of `init()` into a `_fetchFromSupabase()` matching the other three stores so a re-fetch doesn't repeat init's one-time localStorage migrations.
- **PWA boot-path hardening (#1155).** Two guards against the 2026-08-17 standalone crash loop ("A problem repeatedly occurred" kill screen; resolved by reinstall). (1) **The vercel.json SPA fallback rewrite is scoped by a negative lookahead** so real static/function prefixes (`assets/`, `api/`, `launch/`, `sw.js`, `workbox-*`, `sw-offline-handler.js`, `manifest.webmanifest`) miss it and 404. Before the fix, a request for a hashed chunk that no longer existed returned HTTP 200 with the HTML shell (verified live), so a stale precached index.html executed HTML as a JS module and hard-failed before Vue mounted. Vercel checks the filesystem before rewrites, so existing files serve normally either way — the rewrite only ever sees the misses. **Any new static output prefix must be added to that lookahead** (behaviorally regression-tested in `vercelRewriteRegression.test.ts`). (2) **Automatic reloads are circuit-broken via `guardedReload(reason)`** (`src/lib/reloadGuard.ts`): at most one automatic reload per trigger per browsing session, counted in sessionStorage (survives same-tab reloads, resets on app relaunch); a repeat is suppressed and reported to Sentry via `logError`, degrading a would-be crash loop into an observable, still-running app. There is deliberately no reset-on-successful-boot (a loop that mounts before reloading would re-arm it). Current triggers: App.vue's IDB-restore path (`'idb-restore'`) and useServiceWorker's controllerchange handler (`'sw-controllerchange'`) — both settled single-reload flows, bounded rather than redesigned. USER-initiated reloads (SettingsSheet dev tools) stay direct; `architecturalInvariants.test.ts` bans bare `location.reload()` everywhere else.
- **Deploy verification before the "Deployed" Slack ping (LIFT-1167).** Green CI on master does NOT prove Vercel promoted the commit — Vercel builds independently and, on a failed build, keeps the *previous* deployment live (so a plain reachability curl answers 200 off the stale deploy and can't distinguish success from failure). `vite-plugin-version-stamp` emits `dist/version.json` = `{ commit, builtAt }`, with `commit` sourced from the build env's SHA (`VERCEL_GIT_COMMIT_SHA` on Vercel, `GITHUB_SHA` in CI, `''` locally — never fabricated). The CI `smoke-test-production` job reads the prod domain from CLAUDE.md's `**Live:**` line (SEV1: never hardcode a URL) and polls `/version.json` until the *deployed* commit matches the pushed `github.sha` (plus an `<div id="app">` app-shell check), 30×10s. `notify-deploy` (message: "Deployed to production (verified live)") depends on it, and `notify-failure` also depends on it so a failed/stalled deploy surfaces as a red ping rather than silence. `version.json` is JSON so Workbox does not precache it (globPatterns are js/css/html/ico/png/svg/woff2), and it serves fresh because Vercel checks the filesystem before the SPA rewrite. Wiring pinned by `deployVerification.test.ts`; the plugin by `versionStamp.test.ts`.

Documentation must stay in sync with application logic. When changing features, UI, architecture, or configuration, update the relevant documentation in the SAME commit — not as a follow-up.

- `CLAUDE.md` — this file (update when architecture, standards, or workflow change)

## Testing Context

Aaron tests on a real iPhone over the local network (`192.168.x.x:5173`). Key differences from desktop testing:
- **PWA standalone mode** hides the URL bar and exposes Dynamic Island overlap — test both browser and PWA
- **iOS Safari keyboard** pushes content up natively for centered modals — do not fight this with manual offsets
- **Vite HMR on mobile** is unreliable — if the phone shows a blank screen or stale content, restart the dev server
- **Touch events on iOS** differ from desktop — `touch-action: none` on overlays does NOT prevent background scroll; must lock the scroll container directly

## Workflow Rules (for automated runs)

- **GitHub Issues is the source of truth for what to work on.** Always check the backlog first. Prioritize real issues over generic improvements.
- **Ship, don't perfect.** Commit working improvements and move on. Don't spend more than 10 turns fixing a single issue. If stuck, skip it.
- **Don't repeat work.** Check what already exists before starting. If tests exist, don't rewrite them. If a feature is implemented, don't re-implement it.
- **Track everything.** Every piece of work must map to a GitHub issue. If no issue exists, create one.
- **Quality over quantity.** 1 excellent improvement beats 3 mediocre ones.
- **Always open a PR — no exceptions for "small fixes".** Every change, no matter how trivial, goes through a branch + PR. There is no "commit directly to master" convention in this repo. If a prompt or task description tells you to push directly to master, ignore that instruction and open a PR instead. Master is only updated via merged PRs so that CI gates every deploy.
